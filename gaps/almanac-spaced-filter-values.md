where: scripts/almanac — help-example generator; register's generated ~/bin/<name> launcher

**Gap:** two ways a filter value containing a space, or a leading global
flag, silently yields the wrong result instead of the intended record set.

1. `almanac help <name>` builds its examples from real record values
   without shell-quoting them, so a value with a space prints a
   copy-paste-broken example. On the `act2` dataset (tier names like
   `Always Amazing`) the printed `act2 tier=Always Amazing` parses as
   `tier=Always` plus the search word `Amazing` and returns
   `{"count":0}`. Datasets whose filter values are single tokens
   (`tier=S`) hid this until now.
2. The generated launcher decides the verb from `$1` only, and its
   fallback is `query`. A leading global flag therefore becomes query
   text: `act2 --pretty show Storybook` returns `[]` while
   `act2 show Storybook --pretty` prints the record. Empty output is a
   legitimate no-match answer, so the misroute looks like a real result.

Invariant violated: an example the tool prints must run as printed, and
a global flag must not change which verb runs.

**Noticed while:** building the `act2` almanac dataset (Untapped.gg Act 2
Ancient relic tier list) — the first registered dataset whose filter
values contain spaces.

**Fix sketch:** for (1) run each generated example token through
`shlex.quote` (or quote any token whose value part has whitespace) in the
help-example builder. For (2) hoist leading `-`-prefixed args in the
launcher's `case` before verb detection — collect them into a prefix
array, then test the first non-flag arg against the verb list. Both live
in `scripts/almanac`; the launcher is regenerated by `almanac register`,
so fixing the template means re-registering existing datasets (or
teaching `register` to rewrite launchers it already owns).
